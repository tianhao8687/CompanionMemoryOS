# 长期测试耗时增长诊断

后续已完成性能与记忆链路修复及真实复测，见 [长历史记忆与耗时修复](MEMORY_LONG_HORIZON_REPAIR_REPORT.md)。本页保留修复前诊断，不覆盖原始测量。

日期：2026-09-25。基线为 200 轮真实聊天批次 `5da63a2b-5c3f-4f82-890d-15a10209ef6e`。

主要原因已定位：历史增长使证据校验、关系上下文和索引检查产生越来越多的逐条读取；很多读取各自打开 SQLite 连接，并重新执行 WAL 等连接初始化。重复查询被连接初始化成本放大。连接复用对照确认这是主要性能热点。

本次只做诊断和隔离实验，没有修改产品代码、重启日常程序或改动日常数据库。

## 真实 200 轮记录中的增长位置

以下均为每轮统计量在相应区间的中位数，单位秒。不同列的中位数不能直接相加。

| 指标 | 前 40 轮 | 后 40 轮 |
|---|---:|---:|
| 应用完整回复 | 6.132 | 10.609 |
| 全部模型及向量适配器调用之和 | 5.274 | 4.992 |
| 适配器之外的应用时间 | 0.967 | 5.780 |
| 提取调用前的本地处理 | 0.045 | 0.065 |
| 各向量调用前的本地间隔合计 | 0.242 | 0.904 |
| 聊天调用前的本地间隔合计 | 0.623 | 4.751 |
| 最后一次调用结束至回复完成 | 0.049 | 0.086 |

向量接口调用合计在各 20 轮区间的中位数基本保持约 0.047 秒；完整主模型请求字符数前后中位数为 25,605.5 / 24,453.5。增长集中在发送聊天模型请求之前。四次真实重启之后也没有恢复到最初的本地处理耗时。

阶段重建使用测试租约的 `expires_at - call.remaining_seconds` 还原适配器开始时刻，再减去其 `elapsed_seconds`。这两项分别由 `TestControl.begin_call` 和 `model_call` 在边界记录，适用于本批固定租约。测试驱动在回复结束后读取历史、导出状态的时间不在该 trace 的耗时内。

## 函数与 SQL 证据

使用已关闭的合成测试数据库作只读备份，每个诊断实例从相同 200 轮数据独立启动。通过原有 HTTP 聊天入口，使用真实本地 BGE 向量服务；聊天改用离线模型，关闭模型提取，以单独测量本地工作。没有远程模型调用，没有裁剪历史或跳过证据校验。

先做一次 cProfile 定位，再用不启用 cProfile 的计时及 SQL 计数重复验证。延续原有最后会话的三个样本结果一致：

| 一次聊天的操作 | 次数 | 耗时中位数（秒） |
|---|---:|---:|
| 按 ID 查询原始消息 | 4,909 | 0.109 |
| 新建 SQLite 连接 | 3,077 | 0.462 |
| `PRAGMA journal_mode = WAL` | 3,077 | 2.371 |
| 关闭 SQLite 连接 | 3,077 | 0.298 |
| 获取完整关系上下文 | 3 | 2.094 |
| 检查原话向量索引 | 1 | 0.528 |

关系上下文、索引检查的时间包含下层 SQL/连接时间，不能再与上方 SQL 耗时相加。SQL 计时只覆盖 `execute`，不包括随后 `fetchall`、模型构造等。

对应代码路径：

- `companion_memoryos/database.py:27`：`connection()` 在没有外层活动连接时打开新连接，执行四项 PRAGMA，退出时提交并关闭。分散的逐条读取无法沿用已经关闭的连接。
- `companion_agent/relationship/service.py:805`：`get_relationship_context()` 展开全部关系证据、读取来源、检查限制并逐条验证；`_all_evidence()` 包含累积的 interactions。
- `companion_agent/current_state/service.py:365`：两次 `refresh()` 各编译一次关系上下文，最终回复准备又编译一次。本样本共三次，重复读取大量相同证据。
- `companion_agent/evidence_policy.py:27`、`:72`：来源限制与消息依赖检查逐条读取源消息；召回、索引、近期上下文等路径会分别调用。
- `companion_agent/cognition.py:733`、`:764`：每轮遍历现有记忆/原话并逐条查索引缓存。缓存避免重复计算向量，但没有避免历史扫描和分散查库。

数据库只有约 20 MB、400 条原始消息；此时一条回复已触发数千次连接初始化。当前实现的重复工作随历史增长，这解释了短测试不突出、长期连续测试逐渐变慢的现象。尚未用数千轮数据确定其更大规模增长曲线。

## 连接复用因果对照

实验仅在忽略目录下的诊断钩子中调整连接生命周期：同一次请求复用连接，保留每个原有连接作用域的提交、回滚及嵌套事务行为，请求结束关闭连接。没有把整段聊天包在一个长事务里，也没有增加对象缓存或省略校验。

每个条件重复三次，各次都重新从同一合成基线创建实例。下表不含真实模型等待时间。

| 200 轮数据上的场景 | 原连接方式 | 实验连接复用 | 本地流程耗时降低 |
|---|---:|---:|---:|
| 新开会话 | 3.975 秒 | 0.493 秒 | 87.6% |
| 延续最后会话 | 4.052 秒 | 0.501 秒 | 87.6% |

连接数分别由 2,985 / 3,077 次降为 1 次；消息查询次数仍是 4,703 / 4,909 次。六组配对均核对：保存的离线回复、上下文消息 ID、记忆证据及使用模式、回复目标、选用人设示例一致。全部实例正常关闭。

这说明大部分本地时间可以通过数据库访问层优化消除。表中 0.5 秒是隔离离线诊断结果，不能当作修复后的真实模型端到端响应速度，也不代表并发、故障恢复、遗忘/撤回安全性已通过生产修复验收。实际长测与隔离样本的绝对耗时不同，不能直接把其差值当线上收益。

## 修复顺序建议

1. 优先做请求线程内的连接复用，减少反复初始化；保留提交/回滚边界，避免在等待远程模型时持有写事务。
2. 随后减少同一请求内重复的证据读取和关系上下文计算。涉及更新、遗忘、权限或敏感性变化时，缓存必须失效；回复保存前仍重新核验来源。
3. 将索引缓存检查改为批量或增量读取。继续保留原话向量检索与证据约束。

正式修改后再跑完整真实提取/聊天路径、隐私失效与并发回归，并用更大历史规模测延迟。当前阶段是定位完成，尚未发布性能修复。
