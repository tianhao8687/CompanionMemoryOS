# 动态上下文分配与验收记录（2026-10-03）

后续更新：本报告保留本批次原始口径。随后长对话测试补上内置媒体/工具层的文本预算，
并发现新的容量和检索边界，见[长上下文与长对话测试](LONG_CONTEXT_DIALOGUE_20261003.md)。

当前结论：已实现动态分配并验证其收益，但不能认定软件整体达到工业级水准。
来源检索、最终上下文、生成回答、持久化与服务延迟是不同验收层，不能互相替代。

## 改动与根因

原应用先按固定 2,500 token / 12,000 字符截掉检索证据，再拼装 16,000 token 初始消息。
后面的空位无法恢复前面丢掉的来源。现在先完成当前理解、一次有界检索，再决定最终装入：

- 普通聊天候选上限 4,000 token，需要事实的任务上限 8,000；共同受 20,000 字符及内核配置限制。
- 最多六条原话的对照口径保留，不增加检索、查询编码、抽取或生成调用。
- 若完整初始消息超限，在保留候选中做有界预算试装；来源 JSON、使用计划、人格、近期对话、
  当前输入都计入同一个实际序列化计数。角色/历史裁剪后会重新尝试原候选。
- 只有最终接纳的证据才进入持久化回应计划；试装不写使用账本，不改来源或置信度。
- 显式 RecallRequest 的预算不被扩张；边界保留，状态历史缺项必须弃答，最小必需上下文
  仍超限时明确失败。SQLite 记录及其证据、版本、同意、作用域仍是唯一事实来源。

真实进程测试还发现并修复了两个细节：

1. 单次按超额 token 扣预算会过度缩减，因为来源与使用计划的元数据也随证据减少。
   改为有界试装完整消息，每次只接纳实测能装下的组合。
2. 过去与本轮完全相同的任务请求，因字面匹配最好而占掉答案来源名额。
   开放事实检索将这类重复请求排在补充来源之后；沿用已有任务识别，不新增题目关键词，
   不删除请求，也不改变显式原话历史/助手回复查询的用途。

这不是无限扩容。4K/8K 是候选上限，实际可能分到更少；近期对话占满时仍会遗漏证据。
当前计数是 cl100k_base 的本地估算。16K 限制针对初始消息拼装，尚未统一覆盖之后的
AgentLoop 工具定义、工具结果与服务商输出预留，不是完整请求生命周期的硬上限。

## 与工业级验收的差距

1. 两套中文来源命中还需稳定达到目标，并在未用于修复的新问题上复核；来源 Hit@1 和
   真正多跳/英文来源检索仍存在明显差距。此前 LoCoMo FTS Hit@6 为 56.91%，不能用中文成绩覆盖。
2. 上一轮十万条 SQLite 精确向量扫描，串行 P95 约 2.10 秒，八路并发约 19.39 秒。
   本次不改变向量扫描架构，不能宣称高并发低延迟问题已经解决。
3. 尚未完成授权真实模型下的最终答案准确率、语言质量、费用和端到端延迟验收。
4. 工具循环全程预算、长时间稳定性、机器断电/磁盘故障等验收仍不完整。
   多进程一致性、进程中断回滚和 Web 通过均不能替代这些项目。

因此可以说“已有可复现的工程测试、明确的故障修复和边界”，还不能说“整体已达工业级”。
99% 不是被预算上限判定为不可能，也没有因为本次改进就自动达成。
