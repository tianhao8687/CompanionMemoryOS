# 记忆准确率、速度与压力测试（2026-10-03）

本轮以真实 SQLite / ApplicationMemory 和隔离 HTTP 应用进程测试读写，并按失败证据修复、重测。
结果属于本机有界工程验收，不是生产 SLA 认证，也不是模型最终回答准确率。全部新数据位于
自有 `.agent-tests` 目录，没有连接、打开或复制日常 `.agent-data/romance` 数据库，没有远程模型调用。
失败与成功批次均保留；原始题目、对话库、凭证与浏览器截图不加入 Git。

## 测量方法

- 准确率在正常的最多 6 条来源、2,500 token、12,000 字符预算之后计算。
  Hit@1 为第一条是否命中；Hit@6 为前六条是否至少含一个标准来源；Recall@6 为标准来源找回比例；
  All@6 为所有标准来源是否齐全。题目运行失败仍留在分母。
- 中文 PerLTQA 用官方来源文档 ID，完整文档作为导入档案；不等于原生短对话难度。
  原 585 题属于已反复使用的回归集。新增 580 题按预先保存的旧协议排除旧问题 ID，
  仍共享同一来源库，本轮也已复测，不能称作未触碰的独立验收集。
- LoCoMo 使用另一公开语料的原始回合 ID，共 1,527 道有效题，包含需要多条来源的题目。
  原语料不具备可用来源标注等题目按既有协议排除，排除项保存在协议/样本审计中。
- 合成容量测试使用不可由查询推出的保管位置和来源 ID，同时核对答案片段。
  覆盖单对象、四对象、长来源、旧来源和同键但其他关系作用域的错误答案干扰。
  精确合成查询的 100% 不代表自然语言准确率达到 100%。
- 服务负载采用 256 维本地哈希向量、有界线程、闭环请求和零自动重试；记录 P50/P95/P99、吞吐与每个失败。
  延迟包含 SQLite 检索、哈希编码及真实上下文装箱，不包含 HTTP、网络大模型和回答生成。
  压测进程 RSS 包含测试 oracle 等开销。分位数来自有限请求，不当作长时间尾延迟保证。
- HTTP 测试统计实际页面握手、来源写入、历史/状态读取、流式完成、最终模型请求、幂等与重启。
  客户端延迟还含诊断 trace 与持久化历史核验。模型为离线适配器，读取来源正确不等于生成回答正确。

## 根因与修复

| 失败证据 | 根因 | 修复与回归约束 |
|---|---|---|
| 万条历史下四对象查询仅 6/15 次来源齐全 | 原词面排序信息在合并时丢失，通用向量近邻挤占精确来源 | 保留 FTS BM25，并按实际证据片段的查询词稀有度排序；不提高断言置信度 |
| 长来源在词面候选中，但向量分被当作 0 | 不在向量 top-k 被误当成没有相似度 | 对有界词面候选补算实际余弦，沿用身份、作用域、现实层、时间、向量空间与来源复核 |
| 单次万条检索约 30,040 次现实层函数调用 | SQL 过滤逐条在 Python 中解析历史 JSON | schema 9 在原始 SQLite 来源事务内维护现实层派生列及索引；原 metadata/spans 仍为权威 |
| FTS 连接查询存在临时全量排序 | 使用函数排序无法利用 FTS 的排序路径 | 使用 FTS `rank` 顺序，并以真实 EXPLAIN 查询计划回归检查 |
| 十万条四对象查询丢一个长来源 | 候选/最终来源截断过早消耗在同一查询线索的近邻上 | 有界互补选择；仅在相同日期匹配层级内、且不损失字面覆盖时调整，不改变来源资格和预算 |
| 第一版互补选择降低普通题命中率且破坏日期优先 | 把匹配相同词语误当成答案重复，弱新词可越过强证据 | 保留日期层级；新来源至少覆盖同等字面查询信息才可提前。保留该失败批次，不选择性只报最高分 |
| 仅读取状态时聊天报“正在回复上一条” | 只读快照与写入准入共用非阻塞锁 | 分离写入准入与状态锁；等待短读取，已有写操作仍返回 409；测试同线程重入和竞争写者 |
| 全量测试偶发只读数据库快照不同 | 后台合法向量缓存写入与测试快照竞争 | 测试持有 SQLite 写准入锁期间验证只读接口可完成，阻止后台提交干扰；未关闭产品后台索引 |
| 迁移中断后派生列可能已经存在 | 以“列是否存在”判断回填完成不可靠 | 按 schema 版本重试；派生值回填和版本推进共同提交，覆盖失败重试与回滚 |

新增测试不是只检查最终状态字符串：包括精确来源与答案、候选真实余弦、日期排序、SQL 查询计划、
现实层更新/回滚/迁移、读写竞争。此前的事务、删除、同意、隔离和版本链回归继续全量执行。
没有加主题限定词、改回答措辞来掩盖遗漏，也没有增加永久倾听模式、偏好数据库或固定问句配额。

## 验收边界

SQLite 向量后端仍为精确扫描，未引入 ANN；在十万条和并发场景下仍需按实测延迟评估容量，
不能把“没有损坏”解释为“速度达标”。单聊天写者仍是产品设计，409 是拒绝，不计成功吞吐。
本轮未做长期运行、机器断电、磁盘故障、跨机器或真实网络模型的服务等级测试。
进程中断事务回滚验证不等同断电耐久性认证。

没有已批准的真实模型批次，因此最终回答准确率和语言质量保持未验证；
`chat_quality.json` 的离线语言验收按设计返回 blocked / 退出码 2。
Flutter、桌面原生及移动端属于独立环境，本轮没有把 Web 结果当作它们通过。
没有推送 GitHub、上传新 GitHub 产物或触发打包。

## 99% 目标的差距复核

用户追问后，对最终中文 BGE 的全部 43 个未命中做了分阶段对照。首次运行编号
`08bcc0eb-605e-4b29-ac9b-698e9368e0f4` 保留为诊断证据，但之前对该批“扩大到 80 条”的
解释有误：请求被内核 `max_turn_limit=12`、`max_tokens=8000`、`max_characters=20000`
裁限，实际只比较了 6 条与 12 条，不能证明目标不在 80 条候选中。

更正后的独立诊断编号为 `646760cd-8c97-423d-a373-36a03756769b`，证据在
`.agent-tests/recall-diagnosis/646760cd-8c97-423d-a373-36a03756769b/results.json`。
从本轮自有 benchmark 数据库只读备份到新诊断目录，原结果和原数据库不修改，无远程调用。
同一问题依次重放：原 6 条/2,500 token/12,000 字符；6 条/8,000 token/20,000 字符；
12 条/8,000 token/20,000 字符；最后仅在诊断进程显式提高配置上限，测
80 条/100,000 token/500,000 字符。逐次记录实际生效预算并断言；最后一档均未发生预算裁切。
全部原条件重放都与原未命中结果一致。生产配置与正式成绩保持不变。

| 未命中发生阶段 | 原 585 题中的 20 个未命中 | 新增 580 题中的 23 个未命中 |
|---|---:|---:|
| 六条来源中已有正确来源，原上下文预算装不下；仅放宽预算可找回 | 8 | 6 |
| 仅放宽预算仍失败，扩大至 12 条后找回：排序或六条截断问题 | 6 | 11 |
| 在 12 条之外，真实放宽到 80 条后找回 | 5 | 6 |
| 真实扩大到 80 条且放宽预算仍未找回；需继续查候选生成/过滤 | 1 | 0 |

“预算不足”标记不是归因本身：原 20 个漏题中 18 个有该标记，对照只证实其中 8 个在
不改变六条来源上限的情况下可由放宽预算找回。诊断不修改正式六条/2,500 token/12,000 字符
验收口径，也没有把放宽条件后的数字当作新成绩。

585 题达到至少 99% 需正确不少于 580 题，即 20 个漏题至少解决 15 个；580 题的新问题集
需正确不少于 575 题，即 23 个漏题至少解决 18 个。当前没有证据证明 99% 不可达，
也没有证据证明现在已达成。后续要改善证据片段装箱、相关性排序和候选生成，保留来源引用、
隔离、删除与同意检查，并在未用于修复的新题上验证。这里讨论的是来源 Hit@6，
当前原 585 题的 Hit@1 为 75.21%；两者都不是最终模型回答正确率。

## 实际上下文预算核对

以下是动态分配改造前核对的预算，2,500 token 不是整个聊天的总上下文。
用户随后批准的动态方案与对照结果另见 [动态上下文测试记录](ADAPTIVE_CONTEXT_20261003.md)。

| 层次 | 改造前默认 / 上限 | 代码位置 |
|---|---|---|
| 首轮消息拼装总预算 | 16,000 token | `companion_agent/runtime.py` 的 `max_context_tokens` |
| 普通聊天记忆召回 | 2,500 token，同时不超过 12,000 字符；4 条结构化记忆、6 条原话 | `companion_agent/cognition.py` 的 `_recall_for_processed_turn` |
| 内核记忆硬上限 | 8,000 token、20,000 字符、12 条原话 | `companion_memoryos/defaults.toml` 的 `[retrieval]` |
| 近期对话 | 最多 20 条消息，仍受总预算裁剪 | `companion_agent/runtime.py` 的 `recent_turn_limit` |
| 模型默认输出上限 | 4,096 token，与输入预算分开 | `companion_agent/deepseek.py` 的 `DeepSeekConfig.max_tokens` |

首轮 16,000 token 包括角色规则、历史、当前消息和编译后的各类上下文；记忆在前一阶段先按
2,500 token 装箱，整体有余量时不会自动回填已经丢弃的来源。AgentLoop 随后新增的工具定义、
工具记录/结果并未在这个首轮计数点统一重新装箱，因此 16,000 也不是整个 API 请求生命周期
的严格硬上限。当前计数采用 `cl100k_base`，不等于 DeepSeek 服务端的精确计费 token 数。

判断应依据具体任务而非统一行业 token 数：16K 可作为普通聊天的实验起点，但固定 2.5K
记忆配额已造成可复现漏题，不能据此宣称适合复杂长期回忆。可评测 4K/6K/8K 记忆配额，
由整体剩余容量与任务所需证据分配，并统一核算工具开销与输出预留；同时比较命中率、
尾延迟和真实调用费用，不能仅靠增加 token 数宣称解决全部检索问题。
