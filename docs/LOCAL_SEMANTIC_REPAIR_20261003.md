# 本机语义检索、长对话查询性能修复与复测（2026-10-03）

此前 FTS 长测的唯一剩余漏召回，是泛化类别问句与具体偏好原文之间缺少词面匹配。
FTS 与 256 维字词哈希均不具备可靠的类别语义理解；本轮没有添加题目专用同义词，
没有降低匹配阈值、放宽来源限制或把所有偏好强行注入上下文。

原应用只有字词哈希、普通向量 API 与关闭三种选择。离线聊天会将普通向量 API 改为字词哈希，
即使驱动已经明确登记本机 BGE 服务，也不会调用它。因此增加明确的 `local_api` 选项，
使本机预训练语义检索独立于聊天模型模式。旧配置的网络行为保持不变，默认仍为字词哈希；
需要按 [本机向量说明](LOCAL_EMBEDDING.md) 启动服务并选择此选项，不能把默认 FTS 称为已获得语义理解。

本机地址只接受 HTTP 字面回环地址，保留禁止重定向、身份作用域、同意、来源依赖、
版本更正、遗忘及 SQLite 真相源。向量仍是可重建的索引，不引入第二份偏好数据库。
测试实例必须明确登记端点；前台查询、后台分段编码与离线回复使用同一持久化调用账本。

## 长对话延迟增长的根因

本机语义长测虽然解决了漏召回，但暴露出新的查询退化。隔离复制正在测试的合成库，
单次聊天的前台 CPU 剖析显示 5.69 秒中约 3.75 秒在语义索引搜索；这是含剖析开销的诊断，
不作为端到端延迟。追踪实际 SQL 后，`EXPLAIN QUERY PLAN` 显示父表逐条定位来源，
而分段表仅按 `(space, dimensions)` 定位，导致每个来源都重复扫描同一向量空间。

修复把派生索引改为 `(space, dimensions, turn_id, source_hash)`，SQLite 可按完整关联键
定位当前来源的分段。原 SQL、作用域/同意/版本/正文哈希过滤和余弦评分均未改变。
初始化也会为已存在的数据库安装新索引，移除旧的冗余前缀索引；不重建来源记录或改变数据库真相。

在同一隔离库、同一实际 SQL 上，补索引前 **3.742 秒**、补索引后 **0.00853 秒**，
**1,350 行的 ID 与向量字节集合完全一致**。这是单条 SQL 的局部实验，不能当成整次聊天提速倍数。
另用 SQLite 虚拟机指令数建立不依赖机器速度的回归：200 → 400 条来源时，旧版
246,700 → 973,300 条指令，接近四倍；修复后通过线性增长上限检查，覆盖新建和已有库升级。

## 验证方法

在独立工作树保留本轮记忆代码，排除并行开发的品牌资源与记忆小窝，避免把未完成的功能加入提交。
索引修复前后在不同工作树执行，保持各自完整 600 轮期间代码不变。旧证据仍保留在原检出目录，
新证据位于对应工作树的 `.agent-tests/`；上传只包含源码、测试和此处的人类可读摘要。
定向回归覆盖本机实际 HTTP 调用、离线回复、端点限制、累计配额、重启和旧离线无网络行为。
预训练模型使用已有本机缓存，禁用下载；服务及应用子进程由本轮启动并在 finally 中停止。
不读取日常数据库，不调用远程生成模型，不上传原始对话、数据库、测试凭证或截图。

长测问题与前次一致：100 轮预检后完整执行 600 轮；三个约 4,834 字来源的事实分别位于开头、
中间、末尾。每 100 轮另建查询会话，第 200 轮更正偏好，第 400 轮遗忘，每 200 轮真实重启。
每次请求同时检查实际前台语义编码、流完成、存储 ID、原文、来源和完整文本预算。
此处是检索与应用流程验收，不是生成问答正确率。

## 结果

- Ruff、Ruff format 检查通过；mypy 131 个源文件通过。
- 索引修复前全量 pytest：**1261 passed、2 skipped**，366.86 秒；跳过未授权的真实 DeepSeek 调用与主机不支持的符号链接测试。
  两个依赖弃用警告不影响结果。没有把离线输出当作生成质量评分。
- 最终索引修复后全量 pytest：**1263 passed、2 skipped**，391.77 秒；新增的新建/已有库查询增长回归均通过。
  跳过原因和两个依赖弃用警告与修复前相同。
- 索引修复前、后 100 轮本机语义预检均 **passed**，各 106 次 HTTP 请求；累计适配器调用分别为
  573、572 次，远程调用均为 0。原泛化偏好问题与四个档案来源检查均通过，
  最大文本输入分别为 15,904、15,905 token。
- 索引修复前、后 600 轮均 **passed**：每批 600 条主体输入，共 382,554 字符，
  加上初始偏好与检查问句，各 **631 次 HTTP 聊天**。各有 **24/24 来源读取、6/6 偏好检查、
  6/6 历史核验、3/3 重启检查通过**。早期长文开头、中间、末尾的事实在第 600 轮仍可找回。
- 两批的 631 次请求均核验持久化 ID、回复关联、当前输入完整性、文本预算及没有远程调用；
  **631/631 次前台查询都记录了实际 512 维语义编码**，没有把 FTS 降级算作语义成功。
  每批最终持久化账本均为 3,144 次适配器调用、631 轮、0 次远程调用，低于
  3,800 次调用 / 700 轮 / 3,000 秒的批次上限，无自动重试。
- 600 轮最大文本输入：索引修复前 **15,999 token**、修复后 **15,993 token**，均未超过 16,000。
  这是本次纯文本请求按应用计数器核验的预算，不是所有模型的原生 token 或完整多模态预算证明。
- 生命周期实际进程验收通过；Edge 实际控件、流完成与持久化关联通过。
- `chat_quality.json` 的后端通过；语言评审仍为 `blocked`，需要另外授权真实模型批次。

原 FTS 600 轮失败批次继续保留为失败：来源读取 24/24、偏好检查 5/6，失败项为第 100 轮
泛化偏好查询。三批 600 轮的完整主体语料及泛化偏好问句均一致，未改题目、加入提示词或更换答案。
主体语料按 UTF-8、字段排序、紧凑 JSON 序列化的 SHA-256 为
`00a6b227011dcab5bad98a0ae2267fcdad16ba4bb03264ec2244523b1621b819`。
