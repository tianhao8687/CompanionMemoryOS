# 0.2.23 Windows 点歌与静默启动修复

版本：0.2.23+26。日期：2026-10-16。

后续实测发现本版仍遗漏“点歌抬高已有窗口”的路径。冷启动和复用验收不能代表这条路径通过；
根因、修复及独立窗口层级验证见 [0.2.24 修复记录](MUSIC_0224_WINDOWS.md)。

## 解决的问题

先前“交给网易云”成功，仅说明创建传令进程成功。临时 MCP 会话的 Windows Job
随后结束传令进程，导致播放器一直停在旧歌曲。新版本将两个固定的内置启动工具放到
常驻引擎执行，歌曲指令有时间完成交接，网易云也能独立于工具和心隅运行。

静默启动在创建进程时使用 `SW_HIDE`。心隅 Windows 窗口在前台时，使用有界的焦点保护；
新创建的网易云窗口保持隐藏。已经可见的播放器不会被缩小。保护最长 12 秒，关闭心隅
会清理；用户主动切换应用时系统允许切换，后台保护也会让出控制。
“打开应用”先检查安装路径对应的已有窗口，包括隐藏的托盘窗口；已运行时直接复用，
不再发出会把原窗口唤到前台的重复启动命令，不改变歌曲或播放状态。

初次启动时，Windows 媒体会话可能尚未出现。只在刚刚成功提交歌曲请求、且已经获得
读取权限的情况下继续有限核对，不再把这个启动间隙当作最终失败；不会重复发送点歌命令。

这次没有修改网易云安装文件、图标资源或系统持久设置。开发阶段的最小化兜底已撤回。

## 保持的边界

- 仅当前安装目录下的固定内置网易云启动工具使用宿主执行，第三方 MCP 清理方式保持不变。
- 工具定义及参数仍走同一 FastMCP 实现，执行前核对定义指纹。
- 权限、用户选歌来源、动作记录和幂等仍在原 ToolHub 路径执行。
- 创建进程仍不等于播放成功。卡片只有取得实际媒体证据才显示已验证播放。
- 本次为 Windows 修复包；没有重新打包 Android，也没有使用手机实测结果作背书。

## 失败记录与修正

`music-cold-0223-4f2b46dc241e443ea67489d9dd3790f5`、
`music-cold-0223-4b0b3861fa424fccb7ba8d7408a3d6ea` 未成功建立测试窗口前台条件。
`music-cold-0223-cf201050de234c069d2c9581ad8a7634` 受到用户手动重开/操作影响，
用户已确认，不能用来推断全部播放行为。
`music-cold-0223-94e13a3ff792456f82b92f57039dc840` 暴露了最小化不符合静默需求，
以及冷启动媒体会话尚未出现便结束核对的问题。以上均保留原始失败状态，未覆盖成通过。
`music-open-0223-e358c5e6b1a04c919a3ce36cb5ffdd00` 发现重复打开正在运行的客户端
仍会激活原窗口；该轮也未建立心隅前台条件，不能作为冷启动结论。已增加复用检测并用最终引擎单独验证。

实机尝试的 `--orpheus-startup` 参数没有启动播放器，未纳入最终实现。
最终使用已验证的应用/歌曲命令、`SW_HIDE` 与 Windows 前台窗口保护。
