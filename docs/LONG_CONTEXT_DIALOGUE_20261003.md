# 长上下文与长对话测试（2026-10-03）

本报告保留 FTS 原始失败。后续本机语义接入修复和相同长对话的复测见
[本机语义检索修复](LOCAL_SEMANTIC_REPAIR_20261003.md)。

本轮使用隔离合成数据、实际 HTTP 应用进程、离线回答和本地缓存 BGE；没有远程模型调用，
没有读取日常数据库、启用真实外部动作或上传 GitHub。以下来源命中不等于生成回答正确率。

## 找到并修复的根因

1. **最近来回被永久预留。** 两条单独可处理的长消息叠加时，旧代码无论如何都不移除上一轮，
   导致后续聊天失败。现在先缩减记忆和可选背景、移除更早来回，最后才整组移除未被明确引用的
   最近来回。当前输入不截断，明确引用的原生来回与必要约束不被本次裁剪移除；
   原文保留在 SQLite，本轮遗漏进入资料归属和诊断。
2. **预算计算边界早于实际发送边界。** 媒体协议、工具规则和工具定义在核心编排后追加。
   原 400 轮诊断中，核心日志显示没有超限，但实际消息本身已超过 16K，工具定义还另占约 990 token。
   现在内置适配器提供只读预览，与生成共用转换代码；完整文本消息和工具定义一起参与试装。
   工具循环每一步调用前再次检查，工具结果累积超限就停止，不能继续发出超限请求或重复执行动作。
3. **旧问题挤占答案来源。** 多次询问相近内容后，旧问句的字面匹配高于原始事实，200–300 轮开始漏题。
   现在将纯回忆请求放到独立事实来源之后。统一识别直接回忆指令，排除引用、条件和否定；
   含有独立事实的混合原话仍保留。显式原话历史和助手历史查询保留原用途，不删除记录或抬高置信度。
4. **长来源链触发 SQLite 表达式深度上限。** 首轮长测在第 499 条主会话消息失败。隔离复制失败库，
   用同一消息、同一 request_id 复现到 `latest_reference_feedback`：来源权限查询将近千个来源拼成 OR 树，
   抛出 `Expression tree is too large (maximum depth 1000)`。现在用绑定 JSON 关系做集合匹配，
   查询树深度和参数个数保持固定；反馈查询和采用记录查询都覆盖。没有截掉来源或跳过权限检查。
   1,200 / 20,000 个引用以及真实 1,200 条来源依赖链通过，最后一个来源的禁止引用、时间、用户、
   会话和证据类型隔离仍生效。原失败消息在复制库上原样复测通过。

没有改写用户问句来让测试通过，没有降低来源、版本、同意或身份隔离条件，也没有增加问题次数限制。

## 容量边界

16K 是本地 `cl100k_base` 文本输入预算，包括内置媒体/工具层的文本开销；不是模型服务商完整窗口。
图片 token、输出预留及服务商 tokenizer 差异仍需单独约束。4K/8K 记忆候选额度继续动态分配。

默认应用配置中，约 5,714 字的高密度中文样本加必需规则不能装进 16K。以前这个请求能发出，
是因为少算了适配器开销，不能将其当作成功的预算验证。现在返回明确的 `context_budget_exceeded`：
原文保留，不调用模型，提示分段发送；后续仍能按来源检索该原文。
字符数不是 token 数，因此 API 的 6,000 字符输入校验不保证任意内容都能装进上下文。

连续对话主批次另用约 4,834 字的三个长消息，分别把事实放在开头、中间、末尾。
这不是将原超限失败改判通过：两个长度、原失败和容量边界验证分别保存。

## 方法和结果

SQL 修复后完成同一主会话 **600 轮**，主输入累计 **382,554 字符**，加初始化和检查问题共
**631 次实际 HTTP 聊天请求**。每次的存储关联、当前原文完整性、最终消息与工具定义预算、
禁止远程模型调用检查均通过。600 条主消息全部写入；六次分页历史核验与三次真实进程重启核验通过。
最终主会话有 1,203 条可见消息，其中 1,202 条来自已确认的聊天写入，其余为更正产生的记录。

六个时点各检查三条早期长来源和一条当期短来源，共 **24/24 次来源检查通过**；
最远间隔 600 轮，长材料开头、中间、末尾的事实均能出现在最终模型输入中。
偏好检查 **5/6 通过**，唯一失败是第 100 轮的泛化问句；第 200 轮更正后两次检查、
第 400 轮遗忘后三次检查通过。**整批状态仍为 `failed`**，不把无请求异常或部分项目通过改写为整批通过。
这些是重复事实的来源检查，不是 24 道独立题，也不是生成问答准确率。

另有不依赖档案编号的自然语言检查：三条约 4,600 字材料分别将放映活动的备用电源线位置、
雨天地点和开场音乐放在开头、中间、末尾。立即追问、再聊 24 轮、重启后换会话三次检查，
每次三项事实及来源都在最终模型输入中，共 9/9 个事实快照。最拥挤时完整文本请求为 15,792 token，
其中两项来源通过记忆片段提供，第三项由保留的原生对话提供；不是要求重复注入同一原文。
这仍是同一组事实的重复检查，不是九道独立问答或生成质量评分。

固定场景在首次发送前写入 `long-protocol.json`。全部来源通过真实聊天入口写入；
同一主会话连续发送 600 轮，每 100 轮另开查询会话，检查三个早期长消息和当期短消息。
第 200 轮修改偏好，第 400 轮遗忘，每 200 轮真正重启。核对最终模型输入中的来源 ID 与答案片段、
当前消息原文、消息与工具定义的总计数、流结束及持久化 ID；完整分页历史另做检查。
遗忘导致的明确来源/派生内容清理单独记录，不当成丢失已确认写入。
HTTP 流完成时间与诊断导出耗时分开，不包含真实模型生成耗时；没有推进虚拟时间或冒充实际跨日使用。

FTS-only 的“我现在对饮料的偏好是什么？”在第 100 轮未召回“我喜欢咖啡”。
同一冻结数据库的受控诊断里，给已有记忆卡建立本地 BGE 向量后能召回；问题是词面没有足够匹配，
不是原文丢失。原主测试失败继续计入，不用这个单题对照替代整批验收，也不新增该句的词表特例。
